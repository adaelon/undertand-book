# 修复方案：来源对齐复核过载

状态：Accepted，2026-07-17。适用对象：`understanding-transformer-from-the-perspective-of` 的 390 项来源对齐复核故障及同类公式密集论文。

## 1. 故障基线

当前报告共有 667 个对齐单元，176 个 `verified`、101 个 `format_equivalent`、157 个 `needs_review`、233 个 `md_unmatched`；未解决项 390 个，占 58.5%。其中 203 个 `md_unmatched` 为公式密集内容，41 个 `md_unmatched` 没有可供 LLM 比较的 `pdf_excerpt`。这不是正常内容冲突队列，而是系统性对齐失败。

权威复现输入：

- Markdown：`.understand-book/understanding-transformer-from-the-perspective-of/paper.md`
- PDF：`.understand-book/understanding-transformer-from-the-perspective-of/paper.pdf`
- 基线报告：`.understand-book/understanding-transformer-from-the-perspective-of/.build/source-reconciliation/report.json`
- 输入指纹：MD `865ae650...bfac70a0`，PDF `9391b898...68b9b0`，config `fc78b495...ac0016`

## 2. 根因

1. `latexToDisplayText` 未消除 `mathbb`、`mathcal`、`frac` 等公式表示命令，LaTeX 表示细节泄漏进内容 token，无法与 PDF 的 Unicode/纯文本公式比较。
2. `reconciliationUnits` 只在没有空行时合并公式上下文；常规 Markdown 独立展示公式因此变成缺少稳定正文锚点的单独复核项。
3. `reconcilePaperSource` 找到窗口外唯一 exact 文本后将其计为已解决，却不推进全局单调 `cursor`；后续单元继续在旧窗口搜索，形成级联失配。
4. `getSourceReviewLlmBatchTargets` 把全部未解决项交给逐项串行 LLM，没有识别对齐过载；UI 因而把系统故障显示为 390 项人工任务。
5. fuzzy `needs_review` 候选按 Markdown needle 长度推进 `cursor`；候选不是确定性对齐且 PDF/Markdown 长度不同，游标会越过下一条真实锚点并制造 1.00 分的乱序伪复核。

## 3. 决策

**Decision**: 过载队列先修复并重跑对齐器，禁止批量 LLM。

**Rejected**:
- 降低 fuzzy threshold：会把公式、数字和标识符差异误判为可信。
- 一键接受 Markdown：绕过 ADR-0063 的来源真相门禁。
- 逐项 LLM/人工复核：把系统性失配成本转嫁给用户。

**Constraint**: 过载诊断不得改变 unresolved、trusted 或 manual_override 语义。
**Revisit when**: 批量复核改为具备共享证据的一次多块确定性事务。

**Decision**: 保留原子差异，按 PDF 页面投影用户复核组。

**Rejected**:
- 继续放宽公式等价：会丢失真实运算符差异。
- 把整页合成一个 unresolved：会破坏 source span 与逐条审计。
- 仍要求逐条点击：没有解决用户时间成本。

**Constraint**: 页面操作必须逐条写现有 decision，部分失败可重试且不得回滚成功项。
**Revisit when**: PDF 页面不能稳定承载共享视觉证据。

过载判定是纯派生函数：

```ts
type SourceReviewLoad = {
  overloaded: boolean;
  unresolved_count: number;
  review_group_count: number;
  unresolved_ratio: number;
  unmatched_ratio: number;
  reason: "absolute_count" | "unresolved_density" | "unmatched_density" | null;
};

overloaded = unresolved_count >= 100
  || (unresolved_count >= 20 && unresolved_ratio >= 0.30)
  || (unresolved_count >= 20 && unmatched_ratio >= 0.15);
```

`unmatched_ratio = (md_unmatched + pdf_unmatched) / total_units`。报告缺字段或分母为零时保守返回非过载，不得阻断已有小队列流程。

## 4. 信任不变量

- 只有 exact、compact-equivalent 或 token-equivalent 的确定性前向锚点可以重同步 `cursor`。
- 模糊相似度只能生成证据和 `needs_review`，不得触发重同步或可信输出。
- 公式与相邻正文合并后，公式 token 仍参与等价比较；不能仅凭邻近正文相同就自动接受公式。
- 位于当前 `cursor` 之前的候选不得标记为可信，也不得令游标回退。
- `sourceReconciliationTrusted(report)` 仍只接受 `unresolved.length === 0`。
- ADR-0065 的一次复核后 `manual_override` 契约保持不变。
- 本次仍是 Markdown→PDF 单向覆盖；PDF 独有正文的反向 `pdf_unmatched` 检测是独立信任增强，不混入复核过载修复。

## 5. 实施切片

**切片 1：公式比较与单元形成**

- 做：扩充纯表示型 LaTeX 归一化；让被空行分隔的独立公式携带同节相邻正文上下文，同时保留公式 token 的比较责任。
- 不做：公式语义推理、OCR、模糊自动接受、UI 变化。
- Red：公式密集段落因表示命令和空行被拆成多个 `md_unmatched`。
- Green：同内容的 Markdown/PDF 公式段落成为一个确定性等价单元；真实数字差异仍为 unresolved。
- 验证：`pnpm -C packages/core test -- source-reconciliation.test.ts` 与 Core typecheck。

**切片 2：可信前向锚点重同步**

- 做：窗口外唯一 exact 或确定性 token-equivalent 前向锚点成功时推进 `cursor`；后向候选继续保留为乱序诊断。
- 不做：改 fuzzy threshold、基于 fuzzy 分数推进、跨页语义推断。
- Red：远距离 exact 锚点被计为 resolved 后，紧随其后的差异段仍在旧窗口形成 `md_unmatched`。
- Green：锚点推进后，后续差异在正确页行形成 `needs_review`；后向唯一 exact 不被自动信任。
- 验证：同一 Core 测试与 typecheck。

**切片 3：对齐过载门禁**

- 做：Web 以报告 summary 派生 `SourceReviewLoad`；过载时禁用“LLM 处理全部”，显示先重跑来源对齐的可操作状态；批处理函数自身也拒绝启动。
- 不做：新增持久化 report status、删除逐项人工入口、改变服务端 acceptance。
- Red：390 项快照仍返回全部 LLM targets 并触发 `analyze-all`。
- Green：过载快照不能启动批量 LLM；19 项或低密度队列保持现有行为。
- 验证：`source-review-batch.test.ts`、`SourceReviewWorkspace.test.ts` 与 Web typecheck/build。

**切片 2B：剥离 fuzzy 证据的游标权限**

- 做：`needs_review`/`md_unmatched` 只记录候选证据，不推进 `cursor`；后续单元只能由 exact/compact/token-equivalent 前向锚点恢复位置。
- 不做：丢弃 fuzzy 证据、改变 review 状态、提升 fuzzy 为可信锚点。
- Red：一个较长 fuzzy 差异按 Markdown 长度越过紧随其后的 exact 段，使 exact 段也成为乱序复核。
- Green：只有首个真实差异 unresolved，紧随其后的 exact 段确定性恢复游标；后向候选测试仍绿。
- 验证：Core 定向测试、typecheck 与真实论文 benchmark。

**切片 4：真实论文验收与回归**

- 做：在隔离临时 workspace 用上述固定 MD/PDF 重跑来源对齐，记录前后 summary；运行 Core/Web 全量回归。
- 不做：覆盖现有用户 review decisions、用 LLM 判断修复是否正确。
- 完成：`md_unmatched <= 20`，原子差异投影成不超过 50 个页面复核组，且抽样数字/公式冲突仍保持 unresolved；Core/Web 测试和 typecheck/build 全绿。
- 若 `md_unmatched > 20` 或页面复核组超过 50：不得宣称完成；依据新报告回到责任切片。

**切片 3B：按页人工复核组**

- 做：按 `pdf_page_index` 稳定分组，无页码项各自成组；过载界面显示原子数/页面组数；用户明确点击后把当前页待处理项逐条写为 `accept_markdown`，成功项立即保留。
- 不做：合并 report.unresolved、自动点击、把页面分组当 trusted、重新开放过载批量 LLM。
- Red：122 个 block 仍要求 122 次人工操作；直接多项写入失败会丢失进度。
- Green：真实报告投影为 40 组；一次页面操作逐条持久化且部分失败不回滚，重试只处理剩余项。
- 验证：`source-review-batch.test.ts`、`SourceReviewWorkspace.test.ts`、Web typecheck/build。

## 6. 完成状态机

```text
BASELINE_FROZEN
  -> FORMULA_RED -> FORMULA_GREEN
  -> RESYNC_RED -> RESYNC_GREEN
  -> FUZZY_CURSOR_RED -> FUZZY_CURSOR_GREEN
  -> OVERLOAD_RED -> OVERLOAD_GREEN
  -> PAGE_GROUP_RED -> PAGE_GROUP_GREEN
  -> REAL_PAPER_BENCHMARK
       -> md_unmatched > 20 or page_groups > 50: return to owning slice
       -> workload gates met and regression green: DONE
```

每个切片完成后立即追加 `docs/代码链路.md`；结构或主要数据流发生变化时同步 `docs/架构.md`。最终整页覆盖 `SESSION_CHECKPOINT.md`，写入真实前后统计和可复跑命令。
