日期：2026-09-14。决策：[ADR-0128](adr/0128-root-guided-executor-call-correction.md)。
状态：D0、R1–R4 已完成；编译、日常安装与实时宿主验收见 [R4 记录](performance/understand-book-r4-release.md)。实际原书未续跑。

## 0 对齐与边界

**FrozenIntent**：主任务发现子代理异常后读取实际失败调用，反馈具体错误并恢复可执行工作；交付包括类型化诊断、主任务读取规则、纠错重试和安装态验收。
**授权依据**：用户要求“主任务在这种异常情况应该去阅读 subagent，然后提示 subagent 的错误来重试”，并于 2026-09-14 确认将两个问题落 ADR 和切片方案。D0 授权为文档交付。

**实施授权**：2026-09-14 用户要求“设定goal：阅读checkpoint，实现R1-R3，完成后刷新checkpoint”。沿用已接受术语、读取边界和恢复约束。
R4 授权：同日用户要求“设定goal：阅读checkpoint，实现R4，完成后刷新checkpoint”；包括隔离宿主验收及既有本机安装更新。
**ChangeType**：[边界重构]。主任务诊断读取与纠错反馈扩展旧技能的仅生命周期边界；语义生成和提交权威继续属于 Executor 与 Driver。
**风险承接**：读取完整子代理记录可能包含语义输入；恢复已终止连接可能重复执行。因此读取按失败操作限定，恢复必须与当前 open/commit 状态相容。这是已讨论方案的实施约束，不要求用户选择注册范围。

| 术语 | 状态 | 定义与约束 |
|---|---|---|
| opaque handoff ref、dispatch slot | EXISTING | 沿用 CONTEXT；原始派发引用是纠正参数的来源 |
| recovery generation、semantic attempt | EXISTING | 调用纠错只改变必要的控制恢复身份，不增加内容生成次数 |
| Executor 调用纠错 | NEW | 对实际失败调用给出字段级纠正，恢复原工作目标 |
| 构建诊断读取范围 | BOUNDARY_CHANGE | 允许 Root 读取所属 child 的失败调用与控制字段，排除内容载荷 |

术语已对齐，定义见 [CONTEXT](../CONTEXT.md)。领域对齐完成。

## 2 目标恢复协议

```text
child interrupted
  -> Root 读取该 child 的失败调用记录
  -> 比较 issued_request 与 attempted_request，保留原工具错误
  -> 可定位的 open 参数错误：反馈字段、实际值、正确来源
     -> child 尚可继续且连接未绑定：同一工作引用纠正重试
     -> child 已终止或连接不可继续：Driver 核验后签发恢复引用，新 child 执行
  -> 真版本不兼容或非调用错误：沿对应实际诊断处理
  -> 下一次 build.step 确认提交或剩余工作
```

主任务采用已有任务读取能力查看**失败 child**，优先请求不含语义输出的调用记录。最小读取字段为 child 身份、工具名、操作阶段、请求版本、open 引用和错误码；不得把整份对话送进 Root。宿主若不能过滤，先提供这几个字段的有界提取，不能以读取全文作为默认实现。其他 operation 的诊断按控制字段白名单读取，不复制 input 批次或 submit candidate。

拟定纠错观察（R1–R2 冻结为具体版本化接口，字段含义以此为准）：

```text
OpenCallCorrection = {
  issued_handoff_ref, attempted_handoff_ref,
  field: "opaque_handoff_ref", phase: "open",
  reported_diagnostic, cause: "invalid_ref" | "different_ref"
}
```

Root 保存工具原诊断与纠错观察两个事实，不把历史 `protocol_incompatible` 改写成 `bootstrap_unavailable`。Driver 只接受本 invocation 已签发、仍 current 的 issued ref，核对 attempted ref 的差异；有效但不同的 ref 还须排除其他已绑定/已打开工作。已有 open、active lease、commit 或 superseded 事实优先，不强制换代、不重复生成。

纠正反馈示例：“上一条 open 的 opaque_handoff_ref 缺少字符；使用附带的原始派发引用。只纠正打开请求，语义任务保持不变。”新 child 使用 Driver 返回的新引用；Root 不自行构造恢复引用。新 payload 允许此有界控制反馈，替代旧技能“只能传 ref、不能附加诊断”的限制。

沿用 ADR-0121 的三次控制恢复上限及明确的耗尽边界；同一失败观察重放不多计一次。相同参数重复失败不能通过换 child 获得无限次数。调用格式检查须在连接绑定前完成，避免无效 open 占住正确任务。

## R1 无效调用分类

**输入/产出**：缺字符的 open、合法版本与真实未知版本 -> 各自准确的工具诊断及连接状态。
**触达**：`skills/build/build-executor-mcp.ts`；`packages/core/src/build-executor-tool-adapter.ts`、`build-executor-connection-capability.ts`、`automatic-build-executor-session.ts`。
**实现**：增加有字段位置的调用格式诊断；保留真实版本不兼容。无效 open 未绑定且连接可继续时允许纠正；已经 terminal 的连接仍拒绝操作。
**红测/验收**：复现 75→73 字符错误；现在不得返回版本不兼容，不产生 durable open/semantic attempt。相同未绑定连接用正确 ref 后可以打开；真实未知版本、已终止连接分别保持对应诊断。
**测试入口**：`packages/core/test/build-executor-mcp.test.ts`、`build-executor-tool-adapter.test.ts`、`automatic-build-executor-session.test.ts`。
**失败处理**：若会在拒绝无效参数前绑定连接，先修检查顺序；不靠放宽引用格式使测试通过。

## R2 持久纠错恢复

**输入/产出**：R1 诊断或历史笼统错误，加实际调用差异 -> 可幂等恢复的 Driver 动作。
**触达**：`skills/build/automatic-build-driver.ts`；`packages/core/src/automatic-build-executor-session.ts`、`automatic-build-attempt-recovery.ts`、`automatic-build-dispatch-runtime.ts`。
**实现**：在已有 open-failure 恢复路径接入窄化纠错观察。终止 child 需要恢复时推进现有控制代际，沿用 slot、工作单元和已接受产物。旧 completed ref 保留，新 ref 才能再次调度。
**红测/验收**：派发正确 ref→错误 open→child 终止→Root 上报→获得可执行替代→一次成功提交；重复上报只推进一次。已打开/已提交/已换代、属于其他 invocation、没有实际差异、三次耗尽均有明确结果。
**测试入口**：`packages/core/test/automatic-build-driver.test.ts`、`automatic-build-dispatch-runtime.test.ts`、`automatic-build-executor-session.test.ts`。使用真实磁盘 store 和现有夹具。
**失败处理**：若历史证据不足，不换代；返回缺少哪项证据，不默认建议重新注册。

## R3 主任务诊断与执行器反馈

**输入/产出**：child interrupted + 所属任务的失败调用记录 -> 精确纠正信息、恢复观察及后续生命周期。
**触达**：`skills/build/SKILL.md`、`skills/executor/SKILL.md`、`agents/automatic-build-dispatch-executor.md`，以及 `plugins/understand-book` 对应技能和专用 agent 资产；复用现有插件生成/校验入口同步内容。
**实现**：明文允许控制记录读取；收到笼统不兼容或与其他成功 child 不一致的打开错误时，先检查实参。活跃且连接可继续的 child 接收同工作纠正；terminal child 走 R2 后由新 child 接受纠正背景与新 ref。主任务不执行 executor.open 代替 child。
**验收**：技能/角色契约测试检查诊断读取范围、真实错误保留、反馈模板、原连接与新连接分支、live slot/完成集合更新。正常成功路径不新增逐 child 读历史。
**测试入口**：`packages/core/test/codex-executor-agent.test.ts` 和 R4 宿主场景。宿主行为不能仅用文本断言宣布通过。

## R4 编译与宿主验收

**输入/产出**：前三刀编译程序、插件资产和隔离小书 -> 可观察的一次调用错误恢复，不要求用户注册或重新确认原计划。
**场景**：在隔离任务中让一个 child 提交缺字符 open；验证 Root 读取的是失败调用、指出缺失字符，原连接可继续时纠正，terminal 分支经 Driver 启动替代 child；最终单元只提交一次。另一个成功槽不受影响。
**证据**：记录初始派发/尝试值、原错误、纠错观察、恢复代际、最终提交数、语义尝试数和宿主是否要求用户操作，不保存语义载荷。未知版本另验应停在真正维护边界。
**交付**：更新代码链路、架构和安装记录。编译测试通过只证明程序路径，真实宿主场景通过才证明主任务会读 child 并反馈。
**恢复原书**：安装资产验收后，从原 invocation 重新读取状态，处理仍 pending 的项；不删除历史记录或重新制定计划。实际续跑另记录结果，不预写 DONE。

## 4 已知边界

- 本方案没有证明 child 接收到的最初消息在哪一层丢字；已证明的是实际 open 参数与派发值不同。
- 只恢复可定位的调用错误；语义候选纠错仍按 ADR-0125，正文与候选不进入 Root。
- 宿主无法提供受限调用记录时，R3 未验收；不能用主任务“知道应该诊断”的文字代替能力交付。
