## 0. 对齐确认单

**FrozenIntent**:解决 `profile_sidecar` 因提示词—Schema 漂移而确定性失败、旧 policy 耗尽污染新 policy、`retry_current` 没有安全恢复 effect 的闭环问题。先修通用契约与尝试身份，再发布新 policy，最后在隔离副本和安装态验证后续跑真实书。不放宽 Schema，不删除历史，不把旧产物迁移当根因。

| 术语 | 状态 | 本方案口径 |
|---|---|---|
| `profile_sidecar` | EXISTING | 当前失败阶段；本次只改其抽取契约投影与 policy release |
| `semantic_attempt` | EXISTING | 同一 policy-bound work unit 的一次模型推理，只在相同 attempt scope 内计数 |
| `policy-bound work unit` | EXISTING | target、stage、work unit 与完整 task policy binding 的合取身份 |
| `retry_exhausted` | EXISTING | 当前 attempt scope 的语义尝试上限已耗尽，不等于 artifact 或全书不可恢复 |
| `retry_current` | EXISTING | 对绑定终态执行恢复校验并重读 durable state；不得无条件清零 |
| `reset` | EXISTING | 历史 append-only 事件；新主路径只能由守卫式 recovery 入口产生等价效果 |

**RiskReceipt**:用户已明确要求解决当前耗尽。接受的约束是：若同一确定性契约仍未修复，点击重试必须继续阻塞；只有 policy scope 已改变，或同 scope 的瞬时故障具备绑定终态的恢复授权，才允许新尝试。

**ChangeType**:`[纯技术]`。不改变 LID、profile sidecar 业务字段、200 字符质量边界、BuildPlan 或用户书籍真相。

领域对齐完成；TermMap 无 `NEW`、`CONFLICT` 或 `UNRESOLVED`，无需修改 `CONTEXT.md`。

## 1. 已证实根因与影响面

### 1.1 契约漂移

当前 `agents/profile-sidecar-extractor.md` 同时存在机器生成合同和手写说明。手写说明把 `problem_framing`、`related_work_positioning` 与合法 `local_function` 混称为 paper “functions”，而严格 Schema 只允许它们进入 `rhetorical_move`。同一提示只要求 `local_summary` 为一句话，没有呈现 `z.string().max(200)`。

当前 `packages/core/src/extractor-contract.ts` 的 writer 契约是确定性的：

```text
local_function  := closed enum without problem_framing/related_work_positioning
rhetorical_move := closed enum containing problem_framing/related_work_positioning
local_summary   := non-empty string, JavaScript length <= 200
```

事故诊断共 21 次：16 次摘要超限，5 次字段枚举非法。最终耗尽单元的三轮依次为摘要超限、`problem_framing` 错填 `local_function`、再次错填同字段。writer 按当前 Schema 正确拒绝，错误发生在 writer 之前的模型可见契约。

### 1.2 尝试身份串账

`packages/core/src/automatic-build-task-store.ts` 的物理目录和 `attemptStates()` 只按 `stage + work_unit_id` 聚合。`AutomaticBuildExecutionIdentityV1` 不含 `input_hash`、`proof_digest`、`policy_set_digest` 或 policy fingerprint；`nextAutomaticBuildExecutionIdentity()` 因而会把旧 prompt policy 的三次失败继续算在新 prompt policy 上。

这与 `CONTEXT.md` 已冻结的“同一 policy-bound work unit”定义矛盾。即使新 prompt 形成了新 policy set，只要 `work_unit_id` 稳定，当前实现仍可能立即返回旧的 `retry_exhausted`。

### 1.3 恢复入口断裂

底层已经支持 append-only `reset.json`，且 reset 后可开启下一次 semantic attempt；但公开链路有两个缺口：

1. `automaticBuildNext()` 暴露的 `record-attempt ... reset` 没有验证诊断类型、policy scope 或恢复证据。
2. `automatic-build-driver.ts` 的 `retry_current` 只持久化决定回执并重读，没有写入任何 recovery effect，所以未发生外部恢复时必然回到同一终态。

直接把 `retry_current` 改成无条件 reset 会把缺口从“无效果”变成“无限放行确定性错误”，因此不采用。

### 1.4 明确非根因

- 不是 Pass2；失败发生在 `profile_sidecar` candidate writer。
- 不是新版插件读取旧版书籍产物；失败任务绑定当前 `profile_sidecar_semantic_units.v2`、`profile_sidecar_output.v2` 与当前 prompt hash。
- 不是旧 policy artifact 不可迁移；当前看到的是旧失败状态被正确恢复，但它被错误地当成跨 policy 共享的尝试预算。
- 不是安装缓存改变了模型候选；安装态 parity 仍必须在发布切片验证，但它不解释现有 `schema_invalid`。

## 2. 冻结不变量

1. `local_summary` 上限保持 200；不以放宽 Schema 消除事故。
2. `problem_framing` 与 `related_work_positioning` 只属于 `rhetorical_move`。
3. prompt、Schema、quality、router 或输入任一改变，都不得继承另一 scope 的语义失败预算。
4. 同一 scope 内三次确定性失败仍必须进入 `retry_exhausted`。
5. attempt、lease、receipt、diagnostic、旧 policy set 和 artifact 全部 append-only；不删除、不覆盖、不改写 target_ref。
6. physical attempt 目录号保持全局单调，semantic attempt 只在 scope 内单调；两者不得重新混为一个数字。
7. root Codex 仍只能看到 bounded projection；candidate、semantic input、私有路径和原始正文不得越过 executor 边界。
8. 新 policy 的 fresh artifact 仍由现有 policy-generation、proof、quality 和 publication gate 判定；恢复收据不等于 artifact 成功。
9. 当前真实书在自动门、隔离回放和 installed-state 验收前保持原样暂停。

## 3. 目标合同

### 3.1 抽取契约单源

用一份类型化字段定义同时构造 Zod 与模型可见合同：

```ts
interface ExtractorFieldContractV1 {
  field: string;
  required: boolean;
  nullable: boolean;
  enum_values?: readonly string[];
  min_length?: number;
  max_length?: number;
  min_value?: number;
  max_value?: number;
  profile_hints?: Readonly<Record<string, readonly string[]>>;
}
```

`profile_sidecar` 至少声明：

```text
local_function.profile_hints.paper =
  research_question | hypothesis | related_work | method_description |
  experiment_setup | evidence_report | result_interpretation | limitation | future_work

rhetorical_move.profile_hints.paper =
  problem_framing | related_work_positioning | method_setup |
  experiment_report | result_claim | limitation_acknowledgement |
  future_work_projection

local_summary.max_length = 200
```

生成器拥有 enum membership、必填/nullable 和边界文本。手写 prompt 只能解释“字段表达什么”，不得再次列举成员或数字边界。`--check` 模式必须能在不写文件时证明 marker block 与 renderer 字节一致。

### 3.2 Attempt scope

```ts
interface AutomaticBuildAttemptScopeV1 {
  version: "automatic_build_attempt_scope.v1";
  target_ref: BuildTargetRefV2;
  stage: AutomaticBuildStage;
  work_unit_id: string;
  task_binding: {
    input_hash: string;
    proof_digest: string;
    policy_set_digest: string;
    policy_fingerprint: ExtractionPolicyFingerprintV1;
  };
  attempt_scope_digest: string;
}
```

```text
attempt_scope_digest = sha256(canonicalJson({
  target_ref, stage, work_unit_id, task_binding
}))
```

V3 claim 必须显式携带该 scope。`AutomaticBuildExecutionIdentityV2`、terminal attempt event 和 lease 必须可互相证明同一 digest。旧 V1 execution/legacy ledger 保持只读，以已有 lease/policy 数据推导 `legacy_inferred` scope；无法无歧义推导时只允许诊断，不得据此创建新 V3 claim。

物理路径继续使用现有单调 attempt 号：

```text
.build/automatic-build/v2/tasks/<stage>/<work-unit>/attempts/<physical-attempt>/
  execution.json   # V1 或 V2
  lease.json
  failure.json     # 终态失败收据；同 scope recovery 的 digest 权威
  result.json
  recovery.json    # 新主路径；旧 reset.json 仍可读
```

`readAutomaticBuildAttemptSnapshot()` 的无 scope 视图仅用于审计。claim、dispatch 和 `automaticBuildNext()` 的耗尽判断必须调用 scoped reader，禁止再用全历史 `failures >= 3` 作为生产门禁。

### 3.3 类型化失败诊断

```ts
interface AutomaticBuildFailureDiagnosticV2 {
  version: "automatic_build_failure_diagnostic.v2";
  category: "schema" | "evidence" | "provider" | "executor" | "budget" | "internal";
  code: string;
  json_pointer?: string;
  expected?: string;
  diagnostic_digest: string;
}
```

`ExtractorContractError` 的 `schema_invalid`、`evidence_out_of_scope` 等稳定字段进入 receipt/event；自由文本只可作为有界显示补充，不参与恢复分支。diagnostic digest 的输入不含 candidate、source text、绝对路径或任意 stderr。

最低恢复分类：

| category/code | 同 scope 可开新窗口 | 必要动作 |
|---|---:|---|
| `schema/schema_invalid` | 否 | 修复并发布改变 schema/prompt policy 的新 scope |
| `evidence/*` | 否 | 修复输入、router 或 prompt，使 scope 改变 |
| `budget/*` | 否 | 走 ADR-0100 recovery/replan，不消费语义 reset |
| `provider/<allowlisted transient>` | 是 | 当前用户决定绑定终态后追加 recovery receipt |
| `executor/*` | 否，默认只开 lease epoch | 走 executor stability recovery；需要重新推理时再显式分类 |
| `internal/*` | 否 | forward fix；不得由用户点击绕过 |

### 3.4 守卫式恢复收据

```ts
interface AutomaticBuildRetryRecoveryReceiptV1 {
  version: "automatic_build_retry_recovery.v1";
  target_ref: BuildTargetRefV2;
  stage: AutomaticBuildStage;
  work_unit_id: string;
  attempt_scope_digest: string;
  exhausted_semantic_attempt: number;
  terminal_receipt_sha256: string;
  diagnostic_digest: string;
  decision_request_id: string;
  action: "open_same_scope_retry_window";
  created_at: string;
}
```

收据写入规则：

- 当前终态必须仍是该 scope 的耗尽态；`terminal_receipt_sha256` 绑定权威 `failure.json` 原始字节，并与 `result.json` 的 scope/diagnostic 交叉一致。
- decision request 必须属于当前 invocation、当前 BuildPlan identity 和该耗尽投影。
- 只有 allowlisted transient failure 可写 `open_same_scope_retry_window`。
- create-only；完全相同重放幂等，不同内容冲突失败关闭。
- 一个收据只解除当前 terminal attempt，下一次失败后需要新的终态与新决定。
- 新 policy scope 不写 recovery/reset；它天然拥有独立的 `semantic_attempt=1`。
- 旧 `reset.json` 继续只读兼容；通用 `record-attempt reset` 不得为 V3 scoped task 创建新恢复。

### 3.5 Driver 状态机

耗尽 decision request 必须额外冻结旧终态，不能只绑定 BuildPlan digest：

```ts
interface AutomaticBuildRetryBoundaryV1 {
  attempt_scope_digest: string;
  exhausted_semantic_attempt: number;
  terminal_receipt_sha256: string;
  diagnostic_digest: string;
  required_recovery: "publish_new_policy" | "authorize_transient_retry" | "operator_fix";
}
```

这些字段可进入 bounded decision record；普通用户投影只显示稳定 code、stage 与 `required_recovery`，不显示路径、candidate 或正文。应用旧 scope A 的决定时，driver 允许当前 scope 已合法变为 B；若仍为 A，则 terminal/digest 必须完全一致。

```text
ACTIVE(scope A)
  -- semantic failure 1/2 --> ACTIVE(scope A, next semantic attempt)
  -- semantic failure 3   --> RETRY_EXHAUSTED(scope A)

RETRY_EXHAUSTED(scope A) + retry_current
  -- current scope B != A -----------------> REPLAN -> ACTIVE(scope B, semantic_attempt 1)
  -- scope A + allowlisted transient ------> append recovery -> REPLAN -> ACTIVE(scope A, next attempt)
  -- scope A + deterministic diagnostic ---> NEEDS_USER(recovery_not_satisfied), zero mutation
  -- stale plan/request/terminal digest ----> PLAN_CHANGED or refreshed boundary, zero mutation
```

`retry_current` 保留兼容 choice id，但 label 改为“Validate recovery and retry”。返回投影须说明 `required_recovery`，不能只写泛化的 “Retry after recovery”。`quality_gate_failed` 与 `executor_instability` 继续走各自 reason-specific validator，不得复用语义 reset 分支。

### 3.6 本次策略发布

修复发布必须同时完成：

```text
profile_sidecar_policy.v1 + old prompt hash + old policy_set_digest
  -> append-only historical generation; remains readable

profile_sidecar_policy.v2 + corrected prompt hash + new policy_set_digest
  -> new profile_sidecar task scope
  -> old exhausted scope does not count
  -> new semantic_attempt starts at 1
```

Schema 版本仍为 `profile_sidecar_output.v2`，因为接受的数据形状没有变化；stage policy version 与 prompt hash 必须变化。若统一 prompt 文件使 discourse 与 formula member 都得到新 hash，两者都按新 policy set 重建/复验，不得谎称 formula 仍看到了旧字节。

**完成判据**:SR1 的类型化诊断断言转绿；mailbox/executor 隐私边界和 bounded-size tests 全绿。

**实测**:类型化 diagnostic 已贯通 extractor、V2 receipt/V3 attempt event、executor session 与 root bounded projection；V1/V2 legacy failure 只读投影为 `legacy_unclassified`，未知异常保持 `internal/writer_failed`。串行验证中 task-store/mailbox/executor-session/driver 40/40、SR2 lease/dispatch-runtime/CLI 回归 31/31、extractor 的 SR3 聚焦断言 3/3 与 Core typecheck 全绿；extractor 全文件剩余 2 条红测只对应 SR5 的 generated contract `local_summary.max_length` 与 paper profile hints，未越界提前实现。

### SR4 守卫式 recovery 与 driver effect

状态:完成，2026-08-11。

**做**:实现 §3.4-§3.5 的 create-only recovery receipt，让 `retry_current` 在恢复已满足时产生有界 effect，未满足时明确阻塞且零 mutation。

**输入/输出**:输入为绑定的 decision request、当前 scoped terminal state 和类型化诊断；输出为 replan、一个合法 recovery receipt，或 `recovery_not_satisfied`。

**触达**:

- 新增 `packages/core/src/automatic-build-attempt-recovery.ts`
- `packages/core/src/automatic-build-task-store.ts`
- `skills/build/automatic-build.ts`
- `skills/build/automatic-build-driver.ts`
- `packages/core/src/automatic-build-recovery.ts`（只扩 allowlisted projection）
- recovery/task-store/CLI/driver tests

**实现约束**:

- `retry_current` 先重算 target、plan、task binding、scope 与 terminal digest，再决定 effect。
- scope 已改变时不写 reset/recovery，直接重载 driver state。
- 同 scope 只对 allowlisted transient category 写 receipt；`schema/evidence/budget/internal` 必须拒绝。
- receipt 与 recovery marker 使用一个 create-only 权威；完全相同重放幂等，冲突内容失败关闭。
- `record-attempt ... reset` 对 V3 scoped task拒绝；仅保留历史/测试兼容读路径。
- stale request、不同 invocation、不同 plan/terminal/scope 均零写入。

**测试**:

1. 当前事故的 `schema_invalid` + 未变 scope：重复点击仍是 `NEEDS_USER/recovery_not_satisfied`，任务树 digest 不变。
2. scope A 耗尽、当前 policy 变为 scope B：同一用户动作进入 replan，B 从 semantic attempt 1 开始，无 reset 文件。
3. allowlisted provider transient：只追加一个绑定 receipt，并开放一轮；重放幂等，第二个不同 receipt 冲突。
4. stale decision、terminal receipt 漂移、diagnostic digest 漂移、伪造 scope 全部失败关闭。
5. `quality_gate_failed`、`executor_instability` 不进入语义 reset 分支。

**不做**:不改 prompt，不把任意 internal/provider code 默认标 transient，不自动替用户确认。

**完成判据**:SR1 driver 红测转绿；driver 仍只返回四种 root action，response forbidden-field 扫描全绿。

**实测**:`automatic-build-attempt-recovery.ts` 已成为 retry boundary/receipt 的单一类型权威，task-store 以 create-only `recovery.json` 精确绑定 scope、耗尽 semantic attempt、权威 `failure.json` receipt SHA、diagnostic digest 与 driver decision request，并与 `result.json` event 交叉校验。相同瞬时 provider receipt 重放幂等且只开放一轮；下一轮失败生成新终态，旧 receipt 不可复用；`schema_invalid`、`provider_failed`、stale/fabricated receipt、伪造 scope 与冲突 receipt 均零写入。scope B 仍直接 replan、semantic attempt 从 1 开始且无 reset/recovery；V3 raw reset 已关闭，legacy unscoped reset 读写兼容用例保持绿色。正常环境串行验证为 SR4 task-store/lease/CLI/driver 44/44、SR2 lease/dispatch-runtime/CLI 31/31、SR3 task-store/mailbox/executor-session/driver 44/44、mailbox/recovery 10/10，Core typecheck 绿色；先前受限 Windows 沙箱中 `spawn EPERM` 的 9 条 `tsx/esbuild` 路径本次全部可执行，仓库内无临时 Vitest 配置残留。extractor 全文件的 2 条 SR5 计划内红测未在 SR4 越界修复。

**回滚**:未写 recovery receipt 时可回退；写入后旧 reader只可忽略并阻塞，不能用 raw reset 覆盖，修复仍走 forward release。

## 6. 确定性验收矩阵

| 维度 | 正向判据 | 失败判据 |
|---|---|---|
| Contract authority | Zod 与 generated prompt 共享 enum/limit 定义 | marker/parity test 红 |
| Field mapping | `problem_framing` 只属于 `rhetorical_move` | prompt lint 红 |
| Summary bound | 模型可见 `max_length=200`，writer 同值 | contract test 红 |
| Same-scope limit | 第 3 次 terminal semantic failure 后耗尽 | claim 被拒绝 |
| Cross-policy isolation | scope B 从 semantic attempt 1 开始 | 仍读 scope A 耗尽即失败 |
| Physical history | attempt 目录号全局单调，旧树 digest 不变 | mutation audit 红 |
| Active old lease | 新 generation claim 被阻断至 terminal/expiry | 并发双 owner 即失败 |
| Failure typing | receipt/event 保留稳定 category/code/digest | 自由文本分支即失败 |
| Privacy | 无 candidate/source/path/raw stderr | forbidden sentinel 扫描红 |
| Deterministic recovery | 同 scope `schema_invalid` 零 mutation | 出现 recovery/reset 即失败 |
| Transient recovery | exact terminal + decision 只开一轮 | stale/伪造/重复冲突被拒 |
| Scope-change retry | `retry_current` replan，无 reset | 返回旧耗尽即失败 |
| Policy migration | v1 保留，v2 新 digest/rebuild | 覆盖旧 lock/artifact 即失败 |
| Installed parity | Node、Sidecar、plugin prompt/hash 一致 | doctor/release parity 红 |
| Live completion | durable artifact + receipt + stage gate | agent 自述不能替代 |

任一矩阵项为 false，不得执行当前真实书的 raw reset、目录删除或人工 JSON 改写。

## 8. Definition of Done

```text
done =
  extractor_schema_and_prompt_share_one_contract
  AND local_summary_limit_is_model_visible
```
